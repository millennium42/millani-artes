# Spec — DB-006: materializar snapshot lógico SQLite para teste de upgrade

## Objetivo observável

Um teste de integração do harness materializa um snapshot lógico, estático e confiável da versão 1 em dois arquivos SQLite físicos independentes, reabre ambos e comprova schema, dados sintéticos, integridade e isolamento. A fixture é uma origem histórica de teste; não é uma migration de produto nem uma prova de upgrade por migration versionada.

## Motivo

DB-005 comprovou a criação do ledger a partir de arquivo vazio. DB-006 prepara um estado anterior real para testes posteriores de upgrade sem introduzir migrations financeiras ou novo comportamento de produção. O teste usa diretamente o executor SQL existente; DB-007 poderá testar o fluxo versionado que DB-006 deliberadamente não exerce.

## Escopo / Fora de escopo

- Adicionar exatamente um teste em `src-tauri/tests/sqlite_harness.rs` e uma fixture SQL estática `src-tauri/tests/fixtures/db006-upgrade-v1.sql`.
- Em conexão nova, materializar a fixture na primeira chamada de `execute_migration`, fechar e reabrir; validar o estado abaixo. Demonstrar que o segundo arquivo ainda está vazio antes de materializá-lo independentemente, depois reabrir ambos e confirmar isolamento e igualdade do snapshot.
- A fixture versionada no repositório define `main.schema_migration(version INTEGER PRIMARY KEY CHECK (version > 0) NOT NULL)` com a versão 1 e `main.upgrade_fixture(id INTEGER PRIMARY KEY NOT NULL, value TEXT NOT NULL)` com as linhas `(1, "O'Brien")` e `(2, "synthetic-before")`. A aspa é escapada como literal SQL `O''Brien`; não há entrada externa, SQL dinâmico nem dado financeiro.
- SQL de snapshot trusted pode criar o ledger, diferentemente do SQL de migration versionada. Executar a fixture inteira por `execute_migration(conn, include_str!("fixtures/db006-upgrade-v1.sql"))`, em conexão nova e transação única, sem `BEGIN`, `COMMIT`, `ATTACH`, `DETACH` ou `VACUUM` no script.
- Fora: produção, APIs ou módulos novos, migration versionada/API versionada, alterações de dependências/manifests/locks/workflows/records de segurança, banco real rastreado, dados financeiros, startup, plano de produto, backup/restore, setup.exe ou teste de compatibilidade com binário antigo.

## Contrato: entradas, saídas, invariantes, erros esperados

Entradas são dois caminhos independentes dentro do `TempDirectory` existente; cada arquivo começa fisicamente vazio, sem objetos de usuário e com `schema_version(&connection, 1) == 0`. Para cada arquivo, uma conexão nova executa a fixture por `execute_migration` em uma transação única, retornando em autocommit. Após materializar, apenas duas tabelas em `main` existem: `schema_migration` e `upgrade_fixture`. O ledger contém exatamente `[1]`; `table_xinfo` verifica shape integral: ledger tem uma coluna `version`, INTEGER, `pk=1`, `notnull=1`, `hidden=0`, e CHECK positivo no DDL persistido. A tabela fixture tem `id INTEGER`, `pk=1`, `notnull=1`, `hidden=0`; `value TEXT`, `pk=0`, `notnull=1`, `hidden=0`; contém exatamente as duas linhas sentinela ordenadas por id. `schema_version(&connection, 1) == 1` após criação, além da linha `[1]` no ledger. Fechar/reabrir mantém schema, linhas, versão e `PRAGMA main.integrity_check = 'ok'`. O segundo arquivo continua vazio até sua própria chamada; reabrir os dois comprova isolamento. Não inferir que INTEGER PRIMARY KEY rejeita NULL nem acrescentar teste dessa hipótese.

## Critérios de aceite

1. Um único teste novo cria dois arquivos reais com `TempDirectory` e confirma, antes da execução, zero objetos de usuário e versão de schema 0 em ambos.
2. Uma fixture estática checked-in, carregada via `include_str!` e executada com `execute_migration`, materializa somente as duas tabelas acordadas, ledger `[1]`, os metadados/DDL e as duas linhas sentinela exatos; a conexão retorna em autocommit.
3. O primeiro arquivo, fechado e reaberto, preserva shape, linhas, versão 1 e `integrity_check='ok'`; antes da execução própria, o segundo continua vazio/versão 0.
4. Após materialização própria e reabertura, o segundo arquivo tem o mesmo snapshot íntegro e nenhum estado compartilhado com o primeiro.
5. RED usa uma fixture comentada vazia: o teste compila, mas o oráculo falha em runtime (zero objetos/ausência de estado esperado versus snapshot esperado). GREEN preenche somente a fixture com DDL e sentinelas acordados; o teste não muda além de formatação. Sem stub, bug artificial ou mudança de produção; os 18 testes atuais continuam sem mudança observável.
6. Nenhuma alteração de produção, API versionada, dependência, migration de produto, manifest/lock, workflow ou record de segurança; nenhuma alegação de prontidão financeira, startup, backup/restore, setup, compatibilidade com engine antigo ou cobertura Rust global.
