# Spec — DB-010: provar enforcement de foreign keys em arquivo

## Objetivo observável

Um teste de arquivo real comprova que `open_database` aplica foreign keys e que SQLite rejeita referências inválidas em INSERT, UPDATE e DELETE, preservando dados válidos após erros, reabertura e nova verificação.

## Motivo

DB-009 estabeleceu configuração/readback ON por conexão. DB-010 demonstra enforcement sobre schema sintético, sem antecipar migrations ou dados de produto.

## Escopo / Fora de escopo

- Exatamente um teste novo `foreign_keys_reject_invalid_references_in_file`, com `TempDirectory` e API pública `open_database`.
- SQL estático e bindings criam `parent(id INTEGER PRIMARY KEY)` e `child` com FK `NOT NULL`, inserem um parent e child válidos.
- Tentar INSERT de child órfão, UPDATE para parent ausente e DELETE do parent referenciado. Cada operação precisa retornar `SqliteFailure`/`ConstraintViolation` com extended code `SQLITE_CONSTRAINT_FOREIGNKEY` (787). Após cada erro, confirmar estado válido intacto e `PRAGMA foreign_key_check` vazio.
- Fechar/reabrir via `open_database`; repetir estado, enforcement e tentativas inválidas. Não modificar teste anterior de DB-009.
- RED controlado desliga FK somente no novo teste antes da primeira operação inválida; INSERT é aceito indevidamente. Remover essa linha OFF antes de GREEN/commit. O teste final não reativa FK manualmente; usa somente a configuração da API. RED não é bug permanente.
- Fora: produção/schema/migrations financeiras/UI/workflow/deps/records E4/helpers/SQL fixture externo; teste amplo de todos schemas, startup, backup/restore/setup ou cobertura global. DB-011 é independente.

## Contrato: entradas, saídas, invariantes, erros

## Critérios de aceite

1. Um teste novo reutiliza TempDirectory/open_database com schema e registros sintéticos; 21 anteriores permanecem intactos.
2. INSERT órfão, UPDATE para parent inexistente e DELETE de parent usado falham com `ConstraintViolation`/código 787.
3. Após cada tentativa e após reopen, estado válido persiste e `foreign_key_check` fica vazio; enforcement continua ativo.
4. RED OFF controlado só no teste novo aceita indevidamente o primeiro INSERT; remover OFF antes de GREEN/commit. Sem alterar DB-009 ou produção.
5. Nenhuma dependência, schema de produto, helper global, workflow ou record E4 novo.
6. Reexecução E3, review, segurança diferencial, validators e CI no SHA exato passam antes de done.
