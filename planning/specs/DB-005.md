# Spec — DB-005: provar migration versionada vazia em SQLite de arquivo

## Objetivo observável

Dois novos testes de integração no harness existente comprovam a aplicação da versão 1 com SQL vazio em arquivos SQLite reais recém-criados. Cada arquivo passa de schema de usuário vazio e versão 0 para somente o ledger main.schema_migration com a versão [1], e mantém o estado após fechar e reabrir.

## Motivo

DB-004 validou ledger e aplicação sequencial versionada. DB-005 prova a fronteira inicial em arquivo antes de migrations de produto. O teste não declara que uma migration vazia seja migration de produto, nem que startup ou bootstrap de produção esteja pronto.

## Escopo / Fora de escopo

- Adicionar exatamente dois testes em src-tauri/tests/sqlite_harness.rs, reutilizando common::TempDirectory, open_database, schema_version e execute_versioned_migration.
- No primeiro, criar dois arquivos independentes. Confirmar que o primeiro começa como arquivo físico válido, sem objetos de usuário e com versão 0; aplicar versão 1 com SQL vazio pela API versionada; validar ledger, shape, check positivo, autocommit e reabertura. Antes de aplicar no segundo arquivo, comprovar que ele continua sem objetos e em versão 0; aplicar a mesma versão e reabrir ambos para comprovar isolamento.
- No segundo, em outro arquivo recém-criado, aplicar a mesma versão vazia e tentar inserir 1 duplicado, 0 e -1 no ledger. Esperar falha SQLite adequada (chave primária para duplicata; CHECK para valores não positivos, conferindo extended code quando disponível), nenhum registro extra, conexão em autocommit e [1] preservado após reabertura.
- Um bootstrap genérico de schema vazio pode existir somente dentro da suíte de testes. Migrations financeiras/de produto permanecem sob FIN-006, CAT-003 e respectivos work items.
- Fora: API/código de produção novo ou alterado; arquivos de migration de produto; tabelas financeiras; sequência real de migrations; startup/app-data/UI; dependências, manifest/lock, workflow ou records de segurança.

## Contrato: entradas, saídas, invariantes, erros esperados

Entrada: dois caminhos de arquivo separados sob TempDirectory, cada um aberto com open_database; chamada execute_versioned_migration(connection, 1, SQL estático vazio).

No primeiro arquivo, antes da chamada: schema_version(&connection, 1) == 0 e zero objetos de usuário em main.sqlite_schema. Depois: operação concluída em autocommit, apenas o objeto de usuário main.schema_migration, uma linha version=1, e schema_version(..., 1) == 1. PRAGMA main.table_xinfo('schema_migration') tem exatamente uma linha visível: version, tipo INTEGER, pk=1, notnull=1, hidden=0; a definição persistida em main.sqlite_schema.sql contém CHECK (version > 0). Fechar/reabrir mantém shape, versão e PRAGMA main.integrity_check == ok.

O segundo arquivo permanece inicialmente sem objetos/versão e não é afetado pela primeira aplicação. Após sua própria aplicação e após reabrir os dois, ambos mostram apenas seu próprio ledger com [1] e integridade ok.

O segundo teste consulta o ledger com statements parametrizados: duplicata 1 rejeitada como constraint de chave primária; 0 e -1 rejeitados como constraint CHECK. Se disponível, conferir o extended result code SQLite específico; sem ele, exigir ao menos classe ConstraintViolation. Após cada falha, confirmar autocommit e exatamente [1]; fechar/reabrir confirma o mesmo. Não testar NULL: em SQLite INTEGER PRIMARY KEY pode atribuir rowid automaticamente, o que não seria prova de rejeição pelo NOT NULL.

## Critérios de aceite

1. O primeiro teste parte de arquivo SQLite físico sem objetos de usuário, verifica versão 0 e aplica versão 1 via execute_versioned_migration com SQL vazio.
2. A aplicação cria somente main.schema_migration, retorna em autocommit e registra exatamente [1]; table_xinfo confirma a única coluna conforme o contrato e o SQL persistido contém o CHECK positivo.
3. Fechar e reabrir preserva ledger, shape e versão; integrity_check retorna ok. Um segundo arquivo continua vazio/versão 0 até sua própria aplicação; depois, ambos reabrem isolados com [1].
4. O segundo teste rejeita inserção duplicada de 1 pela chave primária e 0/-1 pelo CHECK; verifica códigos estendidos quando disponíveis, autocommit, ausência de linhas extras e [1] após reabertura.
5. São adicionados exatamente dois testes; os 16 casos existentes continuam sem mudança observável e o harness/TempDirectory existentes são reutilizados. A verificação RED documenta um teste novo chamando temporariamente execute_migration(connection, SQL vazio): o oráculo exige versão 1 e falha em runtime com versão 0 versus 1. GREEN corrige somente o caller de teste para a API versionada e adiciona o segundo teste; nenhum bug artificial, stub ou alteração de produção.
6. Sem nova API/código de produção, migration de produto, tabela financeira, dependência, alteração de manifest/lock/workflow/records de segurança ou teste de NULL; não declarar startup, migrations financeiras ou backup/restore prontos.
