# Spec — FIN-008: criar caso de uso de conta

## Objetivo observável
Um caso de uso de aplicação valida e cria uma `Account`, usa persistência SQLite real por adapter e retorna sucesso somente após a gravação confirmada. A conta reaberta contém exatamente ID, nome, tipo e saldo inicial fornecidos/gerados conforme os contratos existentes.

## Motivo
FIN-002/003/004 definiram validação de nome, enumeração de tipo e saldo inicial em centavos; FIN-006 criou a tabela SQLite v3. Ainda não existe um fluxo que alcance a persistência. Esta tarefa conecta esses contratos sem criar regra financeira ou expor SQL à UI.

## Escopo / Fora de escopo
Criar um caso de uso na camada `application` e adapter/repositório na infraestrutura, mantendo o domínio puro. O input contém `name`, `account_type` e `initial_balance_cents`; o caso valida nome com `Account::validate_name`, preserva o nome sem normalização, usa a porta existente `UuidGenerator` para ID e monta `Account`. O adapter mapeia as quatro variantes para as chaves já existentes da migration: `Cash`→`cash`, `BankPix`→`bank_pix`, `Card`→`card`, `Other`→`other`, e executa INSERT parametrizado na tabela `main.accounts`.

A escrita de conta deve ser atômica com o `audit_event` técnico, seguindo MODULE_BOUNDARIES/TRANSACTION_MODEL e DB-014: erro ao inserir conta ou evento não retorna sucesso nem deixa metade persistida. A proposta de tags técnicas é `operation="account_create"`, `entity="account"`; ambas são constantes internas válidas para o contrato de audit_event e não dados da usuária. Reutilizar `execute_write_transaction` e `append_audit_event`; não duplicar mecanismo transacional. Usar `Clock`/`UuidGenerator` já publicados para os campos técnicos necessários, sem escolher implementação global/default.

O saldo inicial é somente o campo de abertura da conta. Não criar movimento de entrada, receita, recebimento, saldo derivado ou outra linha financeira. Não definir sinal permitido, limites, arredondamento, unicidade de nome, capitalização ou normalização além do `validate_name` existente. Não alterar migration 003, domain types/constructors, schema, lockfiles ou dependências. UI, comando Tauri/IPC, listagem/edição, startup wiring e operação no banco do usuário ficam fora.

## Contrato fechado após review E2 pré-BUILD
Entrada: nome, `AccountType` existente, `i64` inicial e portas injetadas. Usecase valida primeiro com `Account::validate_name`; para nome válido mantém texto/campos sem normalização, gera duas IDs via `UuidGenerator` (conta e evento), consulta `Clock::now()`, converte com `duration_since(UNIX_EPOCH)` e `i64::try_from(as_millis())`. Pré-epoch e overflow viram falhas estáticas antes de chamar o port. Em seguida faz uma chamada a `persist_account_with_audit(&mut self, account: &Account, event_id: [u8; 16], occurred_at_ms: i64) -> Result<(), Self::Error>`; erro associado é opaco. Usecase retorna sucesso apenas quando essa chamada retorna depois do commit. Não inclui payload de erro externo.

Adapter SQLite guarda `Option<Connection>`. Em cada chamada toma a conexão disponível, executa `execute_write_transaction`, e no mesmo callback faz INSERT parametrizado dos quatro campos e `append_audit_event` com tags constantes `operation="account_create"`, `entity="account"`, entidade ID igual ao ID da conta e dados técnicos recebidos. Repõe a conexão no adapter somente após sucesso confirmado; em erro a conexão/contexto é descartado e adapter fica indisponível, retornando erro estático sem payload. Não há retry nem reutilização de contexto após falha. Esse port específico mantém tipos SQLite fora da application e realiza uma operação indivisível; não criar generic unit-of-work nem novo ADR. O review Sol6 medium E2 aprovou o contrato sem P0/P1; a questão arquitetural pré-BUILD está resolvida.

## Critérios de aceite
- Caso de uso em `application` usa `Account::validate_name`, `AccountType`, `initial_balance_cents` e `UuidGenerator` existentes; rejeita nome vazio/whitespace segundo validação existente e preserva nome válido exatamente.
- Adapter real mapeia apenas as quatro variantes aos keys de migration 003 e grava por SQL parametrizado sem alterar DDL.
- Teste de integração executa migrations reais v1/v2/v3 em banco físico temporário via harness existente, invoca o caso de uso e verifica após fechar/reabrir os quatro campos exatos e uma auditoria técnica correspondente.
- Falha de validação não escreve; falha em INSERT/auditoria não confirma apenas uma das duas gravações. Sucesso somente depois do commit.
- Nenhum movimento/receita/recebimento é criado pelo saldo inicial; não há regra de sinal ou cálculo de saldo novo.
- Sem conexão SQLite/SQL na UI ou domínio; sem dependência nova, migration nova, alteração de regra, lock ou limite de coverage.
- Review Sol E2 sem P0/P1; observação P2 histórica corrigida nesta proposta. Security/checks aplicáveis, validators e CI no SHA integrado completos antes de `passes=true`.
