# Spec — DB-007: upgrade versionado de snapshot SQLite

## Objetivo observável

Um teste em arquivo real atualiza o snapshot sintético v1 para v2 pela API versionada, preservando ledger, metadados e sentinelas após reabertura.

## Motivo

DB-006 fornece baseline confiável de teste. DB-007 comprova a aplicação da próxima versão pelo executor existente, sem migration financeira ou comportamento de produção.

## Escopo / Fora de escopo

- Exatamente um teste novo em `src-tauri/tests/sqlite_harness.rs`, usando um arquivo `TempDirectory`.
- Popular v1 via `execute_migration(conn, include_str!("fixtures/db006-upgrade-v1.sql"))` e reutilizar `assert_db006_upgrade_snapshot`.
- Executar `ALTER TABLE main.upgrade_fixture ADD COLUMN upgrade_marker TEXT NOT NULL DEFAULT 'upgrade';` por `execute_versioned_migration(conn, 2, SQL)`.
- Confirmar autocommit, `schema_version(&conn, 2)==2`, ledger `[1,2]`, somente tabelas `schema_migration` e `upgrade_fixture`, e `table_xinfo` integral. A coluna adicionada é TEXT/notnull=1/default SQL `"'upgrade'"`/pk=0/hidden=0; verificar também metadados das colunas originais e sentinelas ordenadas `(1, O'Brien, upgrade)`, `(2, synthetic-before, upgrade)`. Fechar/reabrir e repetir shape, dados, versão, ledger e `PRAGMA main.integrity_check='ok'`.
- RED controlado chama executor não versionado apenas no upgrade: ledger fica `[1]` enquanto oráculo exige `[1,2]`; GREEN altera somente o caller para API versionada. RED comprova detector, não defeito de produção nem stub.
