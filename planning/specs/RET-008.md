# Spec — RET-008: selecionar conta de saída

## Objetivo observável

Validar uma escolha explícita de conta existente para o futuro reembolso e devolver a conta selecionada sem alterar qualquer estado financeiro.

## Motivo

As regras de produto determinam que o reembolso efetivo saia de uma conta escolhida. RET-007 permite parcelas explícitas do excedente reservado; RET-008 fixa a seleção da conta antes da criação do movimento em RET-010.

## Escopo / fora de escopo

- Reusar `Account` e a lista fornecida pelo chamador, obtida pelo caso existente `list_accounts`; aceitar a conta somente quando o ID informado corresponder a uma opção dessa lista.
- Exigir ID explícito. Não escolher conta padrão, não trocar silenciosamente a seleção e não filtrar por tipo de conta ou contexto, pois as fontes não definem essas restrições.
- A lista de seleção não fica restrita às contas usadas nos pagamentos originais da venda. RET-009 cobre a prova focal de seleção de conta diferente.
- Não registrar reembolso, criar movimento, mudar saldo/dívida/devolução, auditar, persistir, escolher contexto, cancelar venda, adicionar UI/IPC ou alterar schema/migration.
- A verificação aqui é de seleção sobre uma lista já lida. RET-010 continua responsável por confirmar a referência dentro da unidade de escrita e pelo FK/transação do movimento.

## Contrato: entradas, saídas, invariantes, erros esperados

- Entrada: ID de conta selecionado explicitamente e slice de contas oferecidas ao seletor.
- Sucesso: retornar a referência à `Account` cujo ID coincide exatamente com a seleção; preservar o ID e metadados sem cópia ou conversão.
- Rejeição: ID ausente da lista, inclusive lista vazia, retorna erro estático opaco. Não há fallback nem primeira conta implícita.
- A função é pura; seleção não muda a conta, seus movimentos, saldo, devolução ou recebível e não cria evento de auditoria.
- O chamador fornece as opções. Neste fluxo, usar `list_accounts`, que retorna as contas persistidas sem filtro. `RET-009` deve comprovar seleção diferente das contas de pagamento da venda.
- A verificação de existência em memória não substitui a validação referencial dentro da transação financeira de RET-010.

## Critérios de aceite

1. A seleção retorna a conta correspondente pelo ID e rejeita ID inexistente ou opções vazias com erro opaco.
2. Nenhum default, fallback, filtragem por tipo/contexto ou vínculo obrigatório à conta de pagamento original é aplicado.
3. Os testes provam preservação da conta escolhida e rejeição sem qualquer efeito financeiro; nenhuma persistência ou saldo é alegado.
4. Spec, work item, roadmap, matrizes, progress log append-only e handoff registram o escopo e os limites; validadores, checks Rust e SECURITY passam.
5. Após os critérios 1–4, validadores, checks Rust e SECURITY locais aprovados permitem registrar done/E3/passes:true como candidato ainda não liberado.

## Testes previstos / coverage afetada

- Teste unitário focal: escolher uma conta entre opções de IDs distintos retorna exatamente a conta selecionada.
- Teste unitário focal: ID não listado e lista vazia retornam o erro esperado, sem mutar as contas.
- `cargo fmt --all -- --check`, Clippy locked com `-D warnings`, `cargo test --locked` debug/release e `cargo audit`.
- Sem alteração TypeScript/UI; não declarar coverage global, smoke ou E2E. O código de seleção é pura aplicação, sem SQLite ou movimento.

## Segurança / smoke ou E2E / evidência necessária

O ID não confiável só é aceito se estiver presente nas opções recebidas. Não registrar ID, nome ou dado financeiro. O movimento futuro continua sujeito a FK e verificação transacional em RET-010. Rodar scans existentes e Gitleaks staged no tree final; CI remoto exato e nota Git são gates de liberação. Nenhuma alegação de UI/IPC, smoke/E2E ou INV-FIN-005 completo.

## Riscos / gate humano

Não há decisão humana adicional registrada sobre tipo, contexto ou conta de origem elegível; portanto a seleção fica vinculada somente às opções entregues pelo chamador (`list_accounts` neste fluxo). Essa leitura é limitada ao requisito canônico “conta escolhida”; RET-009 mantém a prova de conta diferente. Se surgir regra explícita em fonte superior, corrigir a spec antes de ampliar o comportamento.
