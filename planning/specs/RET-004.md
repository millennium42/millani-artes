# Spec — RET-004: migration de devolução por item

## Objetivo observável

A versão 14 do SQLite persiste cada registro de item devolvido, referenciando uma linha de venda existente e mantendo quantidade inteira positiva. Banco novo e upgrade da versão 13 conservam o histórico anterior.

## Motivo e fontes canônicas

RET-001 definiu SaleReturnItem com sale_item_id e quantity; RET-002/003 definiram disponibilidade e rejeição pura de excesso. RET-005 precisa do histórico persistido. DB-005 liberou migrations versionadas e harness SQLite em arquivo.

Fontes: docs/product/BUSINESS_RULES.md, docs/product/INVARIANTS.md (INV-RET-001), docs/architecture/TRANSACTION_MODEL.md, docs/operations/MIGRATIONS.md e ADR-003/004/010/014/017/018. As regras estabelecem devolução parcial por item, quantidade restante e atomicidade; não definem campos financeiros ou associação de reembolso nesta migration.

## Escopo / Fora de escopo

- Adicionar migration aditiva 014-sale-return-items.sql, versão 14.
- Criar main.sale_return_items: id BLOB PK de 16 bytes; sale_item_id BLOB de 16 bytes com FK para sale_items(id); quantity INTEGER > 0; tabela STRICT; FK NO ACTION em update/delete; índice não unique em sale_item_id.
- Uma linha representa um registro de item devolvido; linhas distintas podem referenciar o mesmo sale_item_id para histórico de parciais sucessivas. A migration não impõe limite agregado vendido/restante; validação atual é de RET-005/RET-002 na unidade transacional.
- id é identidade técnica do registro persistido, seguindo o padrão dos registros duráveis. sale_item_id já identifica a venda; não duplicar sale_id.
- Expor versão/SQL por constantes públicas do módulo database e adicionar testes no harness SQLite existente.

## Contrato: invariantes e erros

Migration 14 recebe ledger contíguo 1..13. Após commit: schema_version 14, autocommit, tabela/índice presentes, ledger 1..14, integrity_check ok e foreign_key_check vazio.

id e sale_item_id são BLOB NOT NULL de exatamente 16 bytes; id é chave primária. quantity é INTEGER NOT NULL e maior que zero. Tabela STRICT. O índice de sale_item_id não é unique para permitir mais de um evento parcial por linha vendida. A migration não valida soma de devoluções nem disponibilidade.

Qualquer erro na migration deve fazer rollback integral: ledger permanece 1..13; tabela e índice criados parcialmente não permanecem; objetos/dados anteriores intactos. Remover a colisão de teste permite retry da migration.

## Critérios de aceite

1. Migration versionada 14, aditiva e estática, com somente a tabela/índice definidos; nenhuma migration aplicada é editada.
2. Em SQLite file-backed novo, versões 1..13 e 14 aplicam com ledger contíguo, shape/índice/constraints, autocommit, integrity_check e foreign_key_check.
3. Upgrade file-backed v13 preserva objetos e dados de sales/sale_items; fechar e reabrir conserva v14 e integridade.
4. Constraints rejeitam id malformado/duplicado, sale_item inexistente e quantity não positiva; duas linhas válidas para o mesmo item são preservadas.
5. Colisão de nome do índice após CREATE TABLE prova rollback; após removê-la, retry aplica v14 uma vez.
6. Fmt, Clippy locked, Rust debug, harness release, Cargo Audit, OSV, Gitleaks staged, validadores locais, P-REV e CI source/final exatos passam sem nova dependency, mudança de lock ou alteração de exceções.
