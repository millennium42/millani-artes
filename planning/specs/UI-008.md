# Spec — UI-008: cadastro de produto

## Objetivo observável

Permitir criar pela interface local um produto template ativo, com nome, descrição e preço sugerido, usando o caso de uso e o adapter de produto existentes. A pessoa recebe confirmação somente após a gravação e pode corrigir ou repetir em caso de erro.

## Motivo

UI-001–UI-007 já foram liberadas. O `main` atual em `fc0f0b9bec46c113ccb88d4624be16ad387a70ad` contém os formulários de contas, categorias, entradas, saídas e transferências; também contém `create_product` e o adapter SQLite. Ainda não há formulário React, caller Tauri, comando Tauri nem grant de capability para criar produto. O rascunho antigo de UI-008 dizia que a tela era um shell estático; essa premissa foi corrigida após a inspeção do `main` atual.

Produto continua sendo template, não estoque ou movimento financeiro. Preço sugerido usa centavos inteiros, zero é válido, negativos são rejeitados e não há limite acima de `i64` definido pelo produto. A UI deve reutilizar o parser decimal existente sem ponto flutuante e não repetir a regra autoritativa do domínio.

## Escopo / Fora de escopo

- Acrescentar uma seção de cadastro de produto ao `App.tsx`, usando os estilos e padrões de formulário já existentes.
- Enviar nome e descrição literalmente e preço em centavos decimais como string pela fronteira Tauri; reutilizar `parseEntryAmountCents` se os testes confirmarem o mesmo contrato.
- Acrescentar `create_product` em `product_setup.rs`, chamando `application::create_product` e `AdapterSqliteProductStore`, com mutex e `AppDatabaseWriteLock` compartilhados, recuperação após falha e erros estáticos.
- Autorizar somente esse comando na capability local existente `main-local-deny`, sem capability de plugin, shell, filesystem, HTTP, SQL ou origem remota.
- Confirmar sucesso após persistência; mostrar validação acessível ou erro genérico sem dados internos; preservar entrada para correção/retry após falha.
- Fora: listar, editar ou desativar produto; catálogo; preço de venda; estoque; venda; movimento/saldo; migration; dependência; novo design system.

## Contrato: entradas, saídas, invariantes e erros

- Nome obrigatório. Vazio ou apenas whitespace Unicode deve ser recusado pelo caso de uso; texto válido é armazenado sem trim/normalização.
- Descrição vazia é aceita; descrição e nome preservam exatamente o texto enviado.
- Preço é texto decimal em reais com vírgula e até duas casas, convertido sem `Number`/float para string decimal de centavos. Zero é aceito. Entrada negativa, malformada ou fora de `i64` é rejeitada. Não criar teto de negócio arbitrário.
- Wire payload contém somente `name`, `description` e `suggestedPriceCents`. Rust converte string canônica em `i64`; valores não canônicos/fora do tipo falham com código estático antes da aplicação.
- O caso de uso autoritativo continua `create_product`; React não acessa SQLite, não valida regra de domínio, não cria estoque nem lançamento.
- Sucesso limpa o formulário e anuncia confirmação com `role=status`. Falha mantém os valores, associa erro ao campo ou apresenta erro genérico com `role=alert`, sem expor SQL, paths, stack traces ou dados internos. Cliques repetidos durante submissão não geram gravações duplicadas.

## Critérios de aceite

1. A UI exibe nome, descrição e preço sugerido com rótulos, texto de ajuda e mensagens associadas; teclado e foco permitem corrigir o campo inválido.
2. Nome com whitespace Unicode é rejeitado no servidor; nome/descrição válidos preservam os bytes/caracteres enviados; descrição vazia é aceita.
3. Preço zero e valores decimais são convertidos exatamente para centavos inteiros; negativos, sintaxe inválida e overflow `i64` não chegam à aplicação; nenhuma conversão usa ponto flutuante.
4. O comando `create_product` reutiliza o caso de uso e o adapter liberados, passa pela trava de escrita compartilhada e recebe somente grant local da webview `main`; nenhuma capability ampla é introduzida.
5. Testes file-backed SQLite provam produto ativo + um audit atômicos, campos preservados, ausência de efeito em movimentos/saldo/estoque, rejeição sem escrita e rollback/recovery/retry após falha sintética.
6. Sucesso só é anunciado após o comando concluir. Erros são compreensíveis, acessíveis e sanitizados; falhas preservam os dados digitados e permitem retry.
7. Testes React/API, autoridade Tauri e integração Rust passam. A inspeção manual do build Tauri real usa perfil temporário e dados sintéticos; verifica estados, teclado/foco, contraste aparente, overflow em 1024×720 e no mínimo configurado 313×343. Não declarar conformidade WCAG global.
8. `npm run quality`, `npm run build`, `cargo fmt`, `cargo clippy --all-targets -- -D warnings`, testes Rust debug/release, Cargo Audit e scans aplicáveis passam; thresholds existentes são preservados. Como preço é dado monetário, aplicar a regra crítica 95/95/95/90 somente aos arquivos novos `ProductForm.tsx` e `productApi.ts`, além do global vigente 90/90/90/85.
9. P-REV read-only revisa o diff final; CI source/final remoto é verificado nos SHAs exatos; o recibo `released` é publicado e lido de volta antes de iniciar UI-009.

- Vitest de `ProductForm`: zero, decimal de uma/duas casas, valor grande/overflow, negativo, sintaxe inválida, whitespace Unicode, payload preservado, sucesso, falha, foco/ARIA e bloqueio de duplo submit.

- Teste de autoridade compilada: `create_product` permitido apenas na configuração local atual e negado em origem remota, window/webview não selecionados e comandos não concedidos.
- Vitest global: manter 90/90/90/85; glob por arquivo `ProductForm.tsx` e `productApi.ts`: 95/95/95/90 com `perFile: true`. Não diminuir thresholds se houver falha.

## Segurança / inspeção / evidência

Dados exclusivamente sintéticos. Reusar capability existente com permissão estreita gerada para o comando novo; sem plugin ou acesso direto a SQLite na UI. Erros técnicos não atravessam a fronteira. Executar checks/testes e scanners presentes no fluxo do repositório e revisar o grant/allowlist. Para E3, registrar comandos, ambiente, perfis de teste, screenshots sanitizadas se úteis, SHA e limitações; a inspeção visual não substitui os testes file-backed nem a CI.

## Riscos / gate humano

Os formulários atuais compartilham uma página longa; a nova seção pode ampliar a rolagem vertical. Verificar foco e overflow nos dois tamanhos aceitos da janela. Tauri usa `main-local-deny`; não ampliar a topologia. A implementação não altera schema nem migration. Nenhuma gravação deve usar o banco pessoal: testes usam diretório temporário e inspeção nativa deve receber `LOCALAPPDATA` temporário verificado.
