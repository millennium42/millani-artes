# Spec — DB-004: registrar e selecionar versões de schema SQLite

## Objetivo observável

O core lê e valida o ledger canônico `schema_migration` e aplica somente a próxima migration aprovada, registrando a versão na mesma transação do SQL. `schema_version` empresta `&Connection`; em erro, o handle continua pertencendo ao chamador, que deve interromper operações de schema incompatível. Somente APIs `execute_*` consomem a conexão e a fecham em erro.

## Motivo

DB-003 fornece a fronteira transacional para SQL interno. DB-004 adiciona identificação e aplicação sequencial de versões; não seleciona nem executa um plano recebido de UI/IPC. DB-005 continua responsável por sua própria prova de migration em banco vazio.

## Escopo / fora de escopo

APIs públicas:

- `schema_version(&Connection, supported_version: u32) -> Result<u32, MigrationError>` inspeciona o ledger até o limite compilado/confiável informado pelo chamador.
- `execute_versioned_migration(Connection, version: u32, sql: &'static str) -> Result<Connection, MigrationError>` aceita exclusivamente a próxima versão e grava o ledger atomicamente.

O ledger canônico é `main.schema_migration`, com uma coluna `version INTEGER PRIMARY KEY CHECK (version > 0) NOT NULL`. A inspeção consulta `main.sqlite_schema` e `PRAGMA main.table_xinfo`, exigindo exatamente uma coluna chamada `version`, declarada `INTEGER`, `pk=1`, `notnull=1` e `hidden=0`; não autentica nem prova o CHECK. Isso rejeita colunas adicionais geradas e impede que TEMP sombreie main. A consulta de valores é ordenada e streaming, sem carregar o conjunto inteiro; valida inteiros positivos, conversão sem overflow para `u32`, sequência contígua `1..=N` e `N <= supported_version`. Ledger ausente ou ledger vazio significa versão 0 somente quando não há outros objetos de usuário além do ledger. Ausência do ledger com outros objetos, view inesperada, shape divergente, coluna ausente, row malformada, valores duplicados, gaps, negativos, texto, fora do limite ou futuro resulta em `InvalidSchemaState`. Não inferir nem converter automaticamente bancos legados.

Na aplicação, versão 0, replay, gap ou versão que não seja exatamente `current.checked_add(1)` resulta em `InvalidVersion`. Se current exceder a versão suportada, retornar `InvalidSchemaState`. Ler versão dentro da transação; criar o ledger se ausente; executar SQL de migration e inserir `version` com parâmetro, tudo na mesma transação. Refatorar privadamente a fronteira de DB-003 para compartilhar a transação entre os dois fluxos, sem duplicar begin/rollback/commit. Manter `execute_migration` existente e seus nove testes sem mudança observável.

SQL é trusted, interno, estático e revisado; não pode controlar a transação, alterar o ledger, usar `ATTACH`, `DETACH`, `VACUUM` ou efeitos externos. Não há parser ou sandbox. Não armazenar hash/checksum nem comparar o SQL já aplicado: imutabilidade é governança, review e Git. Sem retry automático. `schema_version` é inspeção fora da transação de aplicação; não prova locks ou concorrência global.

## Contrato: entradas, saídas, invariantes e erros

- `schema_version` retorna 0 somente quando não há outros objetos de usuário além do ledger ausente/vazio, ou `N` após validar integralmente as versões `1..=N` dentro de `supported_version`. Em erro, o chamador retém a conexão e deve cessar operações que dependam de schema compatível.
- `execute_versioned_migration` aceita somente a próxima versão; erro de versão ou estado do ledger não altera o banco. Leitura da versão, criação do ledger, SQL da migration e insert parametrizado são atômicos.
- Se o SQL falhar ou o insert do ledger falhar, rollback é exigido; nos casos testados, reabrir mostra schema, dados e versão anteriores. Commit confirmado é pré-condição para devolver a conexão. Erros das APIs `execute_*` consomem/fecham a conexão; erro de `schema_version` deixa o handle com o chamador.
- `MigrationError` mantém as quatro variantes de DB-003 e adiciona `InvalidVersion` e `InvalidSchemaState`. Todas têm `Display`/`Debug` estáticos, `source=None`, sem SQL/path/payload e sem log. RollbackFailed não promete recuperação de I/O ou hardware.
- O chamador fornece `supported_version` compilada/confiável e escolhe somente migration pendente de plano conhecido. Não é API para UI/IPC nem garantia global sob concorrência.

## Critérios de aceite

1. Schema vazio sem objetos de usuário retorna 0 sem criar objetos; ausência de ledger junto de objetos de usuário é rejeitada.
2. Aplicar versões 1 e 2 cria o schema e ledger esperados; dado parametrizado `O'Brien` sobrevive a reabertura e o ledger contém `[1, 2]`.
3. Rejeitar versão 0, replay, gap, metadata inválida, view/shape/coluna incorretas, tipos inválidos, negativos, duplicados, gaps na sequência e versões acima do máximo; estado permanece inalterado.
4. Falha de SQL após DDL+DML e falha real no insert do ledger, provocada por trigger de fixture `RAISE(ABORT)`, revertem schema, dados e ledger; reabrir demonstra estado anterior.
5. Erros das seis variantes são estáticos e opacos em `Display`/`Debug`, sem source nem log; erros de `execute_*` consomem a conexão, enquanto erro de `schema_version` preserva o empréstimo/ownership do chamador.
6. Reutiliza `TempDirectory`, harness e rusqlite existentes. API `execute_migration` e nove testes existentes continuam sem mudança observável; sem dependency/feature/unsafe/timestamp e sem edição do workflow.

## Riscos / gate humano

Uma migração de versão indevida pode tornar o schema incompatível; por isso o chamador limita versões suportadas e só executa o próximo item de um plano compilado. Banco legado sem ledger não pode ser presumido como versão 0. O contrato não exige novo aceite humano. Estado atual E3, `in_progress`, `passes=false`, `humanGateRequired=false` enquanto CI de entrega e validação final não forem concluídos.
