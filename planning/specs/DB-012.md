# Spec — DB-012: rollback genérico SQLite

## Objetivo observável
Materializar e verificar o contrato de rollback do executor `execute_write_transaction` existente, incluindo falha de callback, falha no COMMIT e encerramento abrupto de processo com journal DELETE.

## Motivo
DB-011 comprova a API transacional, mas declara explicitamente que não prova rollback composto. INV-FIN-006/007 exigem atomicidade como infraestrutura; consumidores financeiros e auditoria permanecem trabalhos futuros.

## Escopo / Fora de escopo
Adicionar testes físicos de integração usando banco temporário e reopen, sem alterar produção final, dependências, workflow, schema, migrations, flags SQLite de produção ou contratos existentes. Os testes podem configurar `cache_spill`, `cache_size` e `journal_mode=DELETE` para produzir o cenário físico. Cinco cenários: (1) validação dentro da transação retorna `DomainError::InvalidInput` sem escrita; (2) escrita e DDL parciais seguidas de erro real de constraint resultam em `OperationFailed` e estado original após reopen; (3) FK deferred falha em COMMIT após outras escritas, resulta em `CommitFailed` e estado original após reopen; (4) panic após escritas é capturado por `catch_unwind` e snapshot permanece; (5) subprocesso encerra com exit code 86 sem Drop após `cache_spill`/hot journal em modo DELETE, e reopen recupera baseline.

Rollback é cancelamento SQL da unidade ativa. Se rollback real falhar ou não houver gatilho estável/prova física, registrar o limite: a API descarta a conexão e não promete restauração nem retentativa. A saída abrupta cobre somente o caminho exercitado de journal DELETE; não representa power loss, `panic=abort`, WAL ou recovery global. Referência primária: [SQLite locking and hot journal](https://www.sqlite.org/lockingv3.html), seções 4, 4.1 e 5. Fora do escopo: produção final, consumidores financeiros, `audit_event`, DB-013/014, backup/restore, recovery global e garantias para outros modos de journal.
