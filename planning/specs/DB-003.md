# Spec — DB-003: executar migrations SQLite transacionalmente

## Objetivo observável

O core aplica um script interno de migration em uma transação SQLite e devolve a conexão somente após commit confirmado. Em qualquer erro, a conexão consumida é descartada e não pode ser reutilizada em estado incerto.

## Motivo

DB-002 abre arquivos SQLite reais. DB-003 define a fronteira transacional para executar SQL de migration; seleção e registro da versão do schema pertencem a DB-004.

## Escopo / fora de escopo

Expor `database::execute_migration(Connection, &'static str) -> Result<Connection, MigrationError>` usando a API `Transaction` do `rusqlite` existente. O SQL é estático, interno, compilado e revisado pelo código chamador. O contrato não é parser, sandbox nem permissão para executar SQL recebido de UI, IPC, arquivo ou outra fonte externa.

Aplicação bem-sucedida confirma commit antes de devolver a conexão. Se a aplicação falhar, tentar rollback explicitamente; se rollback falhar, retornar `RollbackFailed`. Falha ao iniciar, aplicar, confirmar ou reverter usa `BeginFailed`, `ApplyFailed`, `CommitFailed` ou `RollbackFailed`. Os erros não carregam payload, `source`, SQL ou path, têm `Display`/`Debug` estáticos e não são registrados em log. Em todo erro, não devolver a conexão consumida; descartá-la/fechá-la.

SQL de migration não pode conter controle transacional (`BEGIN`, `COMMIT`, `ROLLBACK`, `SAVEPOINT`), `ATTACH`, `DETACH`, `VACUUM` ou efeitos externos. SQL vazio é uma operação válida sem efeito. Não incluir identificador/versão, tracking de schema, replay, ordenação, startup, UI/IPC, finanças, backup/restore, instalador ou garantia contra perda abrupta de energia.

## Contrato: entradas, saídas, invariantes e erros

- Entrada: conexão obtida por `database::open_database` e SQL `'static` interno, aprovado no código. O chamador garante ordem, confiança e intenção do script.
- Sucesso: aplicar todo o SQL na mesma transação, confirmar commit e devolver a conexão utilizável; SQL vazio devolve a conexão sem alteração.
- Falha ao iniciar transação: `BeginFailed`; falha de aplicação com rollback confirmado: `ApplyFailed`; falha do rollback: `RollbackFailed`; falha do commit: `CommitFailed`. Em todos os erros a conexão é consumida, descartada e nunca devolvida.
- Nas falhas SQL, de início e de commit `BUSY` exercitadas, o teste exige preservar o estado anterior após reabrir o arquivo. Em `RollbackFailed`, o handle é fechado e restauração não é presumida: antes de novo uso, o caller futuro deve verificar integridade/recuperação. Não prometemos recuperação de corrupção ou I/O físico nem isolamento de efeitos externos.
- As quatro variantes são opacas e sanitizadas em `Display`, `Debug` e `source`; nenhuma registra detalhes em log.

## Critérios de aceite

1. API pública tem assinatura de ownership definida e só devolve conexão após commit bem-sucedido.
2. Banco SQLite de arquivo vazio aceita script DDL; fluxo de upgrade de fixture real mantém dado sintético parametrizado `O'Brien` após migration e reabertura. SQL vazio é no-op válido.
3. Falha após DDL e DML reverte ambas as alterações, preserva estado anterior e não devolve conexão.
4. Outer transaction já ativa causa `BeginFailed`; commit bloqueado por reader em outra conexão com timeout zero causa `CommitFailed`; após reabrir, estado anterior permanece. Testes reais não reutilizam a conexão consumida.
5. As quatro variantes têm `Display`/`Debug` estáticos, sem SQL/path/payload, `source=None` e sem log; falha de apply testa rollback explícito. O mapeamento estático de falha de rollback para `RollbackFailed` será revisado; não alegar fault injection de I/O executada.
6. Usa `TempDirectory` e harness existentes com fixtures de arquivo real, sem dependência, unsafe, feature, ferramenta ou workflow novo. Nenhum tracking/replay/order de migration é introduzido.
